# alpha.7 多工作区并行对话规划

状态：负责人已授权实施，当前合同见 [A9-52](../tasks/A9_52_MULTIWORKSPACE_CONVERSATIONS.md) 与 ADR-0319。
基线：main `84d001e17a88bd3389035bc946331b626f0fbf2e`。
证据层级：开发机实现与真实 Electron 验证完成，详见 A9-52 §4。Win7 并发与资源实测均为 NOT_PERFORMED。

## 1. 交付目标

负责人明确指出，当前无法在不同目录同时对话操作。
下一版的核心目标调整为：不同工作区可同时拥有自己的对话和执行任务。
A 目录的任务运行时，用户能进入 B 目录创建对话、发送请求、编辑文件和运行命令。
A、B 任务真实重叠运行，不是切换后串行执行。

负责人同时指出，当前只能先选择工作区，再在该工作区内创建和切换对话。
对话入口需要支持选择工作区，避免每次跨目录对话都先退出当前对话入口。
新建对话时可直接选择已有工作区或打开其他目录。
切换已有对话时可在同一入口选择工作区和其下的对话。
选中对话后，界面同步展示它所属的工作区。

此前“只读浏览历史”的建议不足以满足这一目标。
它改为配套交互，不再作为下一版的完整交付范围。

## 2. 首版范围与后续顺序

| 顺序 | 结果 | 约束 |
|---|---|---|
| alpha.7 主目标 | 不同工作区并行对话及执行 | 至少两个独立工作区完成真实并发链路；最高并发数按 Win7 资源实测确定 |
| 同版配套 | 对话入口内选择工作区、跨工作区切换对话、状态汇总、目标明确的停止和审批 | 切换查看不关闭其他 Runtime、不暂停其他队列、不转移权限 |
| 首版保留 | 同工作区多个对话串行执行 | 不承诺两个可写任务同时操作同一工作区 |
| 后续独立小版本 | 上下文预算提示、整轮 Diff 文件导航 | 不与并发调度捆绑扩展 |
| 单独立项 | 同工作区多写者、完整运行中转向、无工作区咨询、完整 Review | 分别定义文件冲突、恢复与权限语义 |

不同工作区并行与多个原生窗口是两件事。
采用单应用内的工作区选择与对话列表，每个工作区绑定独立 Runtime。
是否额外提供原生多窗口作为展示方案讨论，不把它作为并发功能的必要前提。
本轮实现合同已由 A9-52 与 ADR-0319 登记。

### 2.1 对话与工作区入口

建议在对话切换入口提供工作区选择及所属对话列表。
用户可从 A 对话直接选择 B 工作区的已有对话。
新建对话时可保留当前工作区，也可选择其他工作区。
工作区选择展示名称及路径，避免同名目录混淆。
对话页面持续显示所属工作区，发送前能确认执行目录。

切换已有对话只切换查看目标，不修改它原有的工作区绑定。
已有历史、队列、审批与 checkpoint 继续归属原工作区。
把已有对话迁移到其他目录不纳入本次建议范围。
取消工作区选择时，保留当前对话和草稿，不创建新对话。

## 3. 当前阻断与修改方向

| 当前事实 | 依据 | 规划方向 |
|---|---|---|
| 主进程只有一个 A9 Runtime 与工作区引用 | `main.js` 的 `a9RuntimeInstance` / `a9RuntimeWorkspace` | 按稳定工作区身份管理 Runtime 生命周期 |
| 换工作区需先检查并关闭原 Runtime | `main.js` 的 `onWorkspaceChanging()` | 将切换查看与结束执行分离 |
| IPC 发送者只匹配单一主窗口 | `main.js` 的 `validRendererSender()` | 新设计保持可信发送者与工作区/对话/任务绑定 |
| 第二实例只聚焦旧窗口 | `main.js` 的 `requestSingleInstanceLock()` / `second-instance` | 不把删除单实例锁当作并发实现 |
| 持久化锁已经按工作区路径存储 | `a9-persistence.ts` 的 `acquireWorkspaceLock()` | 保留每工作区单写锁，不扩大为全应用锁 |
| 单个 Runtime 内对话激活和执行状态耦合 | `a9-agent-runtime.js` 的 `loadConversation()` / `assertConversationSwitchAllowed()` | 隔离各工作区状态；浏览态与执行目标分开建模 |

不改变存储引擎、运行时版本或现有 Runner/Policy/审计执行链。
如确需改变公共接口、持久化格式或关闭行为，先由新 ADR 登记。
不同目录不等于安全隔离；同一目录别名、重叠目录和共享 Git 元数据须明确冲突规则。

## 4. 必须保持的行为

- 各工作区分别拥有会话、草稿、队列、执行控制、审批、问询、checkpoint 和托管进程归属。
- A 等待批准或回答时，B 可继续；批准卡片展示并核对真实工作区、对话和操作目标。
- 停止 A 只取消 A 的请求和已绑定进程；不终止 B，不按全局 PID 列表清理。
- 切换标签只改变查看对象，旧回包不能覆盖当前页面，后台结果仍保存到所属工作区。
- Provider 可继续沿用现有全局配置；单次请求绑定所用配置，禁止切换页面改变在途请求或审批含义。
- 请求数、费用和并发资源按全应用汇总，不能给每个工作区重新发放原全局预算。
- 资源不足时拒绝或排队新任务，已有任务的状态和停止入口仍可用。
- 关闭运行中的工作区必须明确处理其任务；退出整个应用须覆盖全部 Runtime 的审计与回收。
- 重启后各工作区恢复为需显式继续，不自动重放队列、审批或文件副作用。

## 5. 可观察的验收条件

1. 在独立 A/B 目录同时启动两个任务，保留开始/结束时间，证明执行区间重叠。
2. A/B 分别创建、修改和验证自己的文件；文件路径、工具 cwd、事件和 checkpoint 归属正确。
3. 停止 A 时，B 持续运行并完成；A 的请求、进程和任务收尾可核验。
4. A 等待批准或回答时，B 仍可操作；错属、过期或旧页面动作被拒绝。
5. A/B 的队列各自保持 FIFO；暂停、失败和继续互不串用。
6. 快速切换查看时，不串流式文本、工具卡片、草稿、Diff 或错误。
7. 同一工作区的第二可写任务被阻断；目录别名与重叠路径不能绕过约定。
8. 单工作区关闭、应用退出和重启覆盖所有 Runtime，原 alpha.6 无重放规则保持。
9. Win7 普通用户实测至少双工作区；记录峰值内存、CPU、子进程和停止响应，再确定并发上限。
10. 在对话切换入口选择 B 工作区及其已有对话，无需先到独立工作区入口切换；A 的运行继续。
11. 新建对话时直接选择 B 工作区或打开其他目录；首个请求的 cwd、会话存储和审批均绑定所选工作区。
12. 同名工作区能按路径区分；切换后显示正确目录并恢复所属草稿；取消选择保留原对话且不产生空对话。

先打通两个真实 Runtime 的 main/preload/IPC/SQLite/Runner 最短链路，再扩展界面与受影响回归。
模型并行可先用有界本地夹具证明调度；外部模型、目标窗口与额外机器另按实际预算授权。
开发机或夹具结果不能冒充 Win7 实机并发 PASS。
